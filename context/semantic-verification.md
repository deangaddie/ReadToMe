# Semantic verification

Use these terms exactly in code, tests, and discussion.

- **Semantic Similarity Check** — embedding-based comparison of two strings (source text vs Whisper transcript) returning a cosine **similarity score** in `[0,1]`. Served by local containers — `read2me-minilm-l6` (8200), `read2me-mpnet-base-v2` (8201) — each exposing `POST /similarity` with `{text1, text2}` → `{similarity}`. Configured like Transcription: many named **configs** (`Name` / `Type` ∈ `{MiniLmL6, MpnetBaseV2}` / `SettingsJson`), one **active**, via `ServiceConfigStore`. Per-config `SettingsJson` carries `BaseUrl` **and** `PassThreshold` (default **0.85**) — the threshold lives with the provider (the two models have different scales). **Pass** = `score >= PassThreshold`. Inputs sent **raw** (no WER-style normalisation — embeddings handle paraphrase/number-words/punctuation natively).
- **Semantic Rescue** — the WER-fallback in verify. When a clip **fails WER** (`wer > WerThreshold`, transcript exists) **and** a Semantic Similarity config is active, source + transcript are sent to `/similarity`. If `score >= PassThreshold` the item is **rescued**: verify flips to **pass** (`verifyOk = true`, no review row), the over-threshold `wer` is **retained**, the reason records the rescue (e.g. `"WER 0.22 > 0.15; rescued by semantic 0.91 ≥ 0.85"`). Else the WER fail stands. **Best-effort, never worsens an outcome**: no active config, or any `/similarity` HTTP/exception, is swallowed (logged warning) leaving the WER fail intact — the semantic container down can never crash/block the queue. Owned by thin **`ISemanticVerifier`** (`PassesAsync(source, transcript, ct)`). A rescued item broadcasts `Verified(Ok: true, Wer, reason, Rescued: true)`; the verify row shows a green check + **"rescued"** chip.
