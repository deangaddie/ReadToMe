# LLM infrastructure

Use these terms exactly in code, tests, and discussion.

- **Constrained completion** — an LLM request whose output is constrained to a JSON schema (llama.cpp compiles the schema to a grammar, so the model cannot emit anything but the schema).
- **Completion Runner** — the single module (`ILlmCompletionRunner`) that runs a constrained completion end to end: streams via `ILlmClient`, publishes the Audio Gen Stream-style broadcast events, stops at the completion scanner, records stream metrics, reports health streaks, and maps failure to an outcome. Every LLM-calling feature (attribution, discovery, book edits, voice prompts) goes through it — never through `ILlmClient` directly.
  _Avoid_: "LLM helper", "LLM wrapper", calling `StreamChatAsync` from feature code
- **Completion scanner stop** — breaking the stream the moment the answer JSON object/array closes (`JsonCompletionScanner`); disposing the stream cancels the request if the model keeps generating.
- **Run outcome** — the Completion Runner's five-way result: `Completed`, `ParseFailed`, `Failed`, `ServiceUnavailable` (managed docker service failure — triggers requeue, orthogonal to answer quality), or `ModelLoading` (a switchable llama endpoint is still loading the target model — bypasses the health reporter so no container restart, and drives an indefinite requeue-with-backoff rather than escalating to the next config). A genuine cancel is not an outcome; it throws through.
- **Token budget** — the output-token floor a request needs (`AttributionTokenBudget`). An answer carries one entry per item, so the budget must grow with the passage; a fixed config `max_tokens` truncates a large batch, and a truncated answer is unparseable. Still sized from the passage's characters, which over-estimates since ADR-0005 (the answer names items by index rather than copying text) — deliberately generous, because truncation costs a whole chunk and headroom costs nothing. Raises the config's `max_tokens` for that request only, never lowers it, and never caps a config that sets none.
- **Health streak** — consecutive-failure tracking per managed AI service (`IAiServiceReporter`); a completed stream clears the streak, a failure may escalate to service-unavailable handling.
- **Throughput Run** — the unit a "total" tok/s is measured over: one attribution queue, one voice-design batch, one settings test send, one voice design. Bracketed by explicit `RunStarted`/`RunEnded` events on the LLM stream bus, published by whichever producer owns the work. **A single request is a Throughput Run of one** — there is no separate "just one request" concept.
  _Avoid_: "queue", "batch", or "session" when you mean a Throughput Run — a voice-design batch of N is *one* run, not N.
- **Generation Rate** — output tokens per second over a sliding 3-second window, derived by **differencing** consecutive chunks' cumulative `predicted_n`/`predicted_ms`. The live "current" figure. Before 3s have elapsed it computes over a partial window rather than reporting nothing.
- **Run Throughput** — a Throughput Run's rate: `Σ predicted_n ÷ Σ predicted_ms` across its requests, broken down by config id. Composed from the same primitives as a single request's rate, never from the server's ready-made `predicted_per_second`, so the two are always arithmetically consistent.
- **Timings Sample** — one chunk's server reading plus its arrival stamp (`LlmTimingsSample`), published by the Completion Runner per timings-carrying chunk so the throughput aggregator can fill its ring and live rate without reading a clock. **Rides its own `EventBroadcaster`, not the `LlmStreamEvent` family**: one arrives per token, and every `LlmStreamEvent` subscriber repaints or journals whatever it receives — joining that family would cost a SignalR repaint per token per circuit. The arrival stamp is on a process-wide monotonic origin, never per-request: a run's ring buckets span the whole run.
  _Avoid_: putting a per-token event on the LLM stream bus; stamping arrivals from a per-request stopwatch.
- **Baseline reading** — a request's *first* Timings Sample. It establishes what later readings are differenced against and is itself **charted as nothing**. `predicted_ms` clocks from the first token, so the interval this reading would describe (start-of-generation → first token) is the one interval the server explicitly never measures: llama.cpp states the first chunk as `predicted_n:1, predicted_ms:0.001`, and differencing it against the origin charts **1,000,000 tok/s**. The sparkline therefore charts from the second reading onward, and a request that yields only one reading (a token-1 abort) contributes **no bucket**.
  _Avoid_: treating the first reading as its own delta ("its counters started at zero" — they did not); clamping the rate, dropping it as an outlier, or flooring the bar height. It is not an outlier, it is not a measurement — so the answer is absence, not a corrected number.
- **Aborted request** — a request that died mid-stream, cancelled or failed. Its last Timings Sample **counts toward its Throughput Run's total**: real work, really measured, and excluding it makes a total less accurate, not more. An aborted stream sends no final chunk, so that last reading is the only record there will ever be — which is what `timings_per_token` is for. The Completion Runner reports it as `StreamAborted`, which carries **measurement only**: the cancel path publishes it alone, and the failure path publishes it *and* `StreamFailed`, because the figures and the error are different facts. A request that died before its first reading reports absence on every field — it stays counted in its config's `req` column but cannot zero the total it joins.
  _Avoid_: publishing `StreamCompleted` for an abort (the stream did not complete, and `ReportSuccess` is not called); widening `StreamFailed` to carry figures (a cancel is not a failure, and `LlmStreamView` renders a `StreamFailed`'s reason in the error colour — a user who pressed Stop must see no error); dropping an abort's reading as "incomplete".
- **Timings Accumulator** — the per-request module (`TimingsAccumulator`) that ingests llama.cpp `timings` chunks and answers rate questions. Replaces the deleted `StreamMetrics`. **Cumulative, not additive**: llama.cpp's per-chunk timings are running totals, so it *replaces* the latest reading and never sums (summing double-counts every token). Pure — it is fed arrival timestamps and never reads a clock.
  _Avoid_: "stream metrics", "token estimate" — nothing is estimated any more; `chars ÷ 4` is gone.
- **Server-measured** — every throughput figure derives from llama.cpp's own `timings`, spanning first token → stream end with model load and queue wait excluded. Where a backend sends no timings, surfaces show **nothing** — there is no fallback estimate, and "0 tok/s" never means "unknown". See ADR 0003.
