# Character attribution

Use these terms exactly in code, tests, and discussion.

- **Character attribution** — deciding which Character speaks a given Character ParagraphItem, via the LLM. A paragraph with unattributed Character items is **unprocessed**; once a Character is assigned it is **processed**.
- **Character Queue** — the background pipeline. User adds paragraphs; `CharacterQueueWorker` drains it, calling `CharacterAttributionService` per paragraph. `CharacterQueueService` holds queue state keyed by `(folder, paragraphId)`.
- **Frozen boundaries** — the rule that a paragraph's ParagraphItems are set by the deterministic import-time split (`ParagraphSplitter`, a quote scan) and only a user may change them. Attribution never re-slices, never creates and never deletes an item; the LLM sees the split as given and answers only who speaks each one ([ADR 0005](../docs/adr/0005-frozen-paragraph-item-boundaries.md)). An item that genuinely holds two speakers is therefore unanswerable, and its speaker is `unknown` by rule — a signal for the user to repair the split, not a case for the model to fix.
  _Avoid_: "re-segmentation", "the model splits the paragraph" (both describe the retired design)
- **Item attribution** — the LLM's answer about one ParagraphItem: `{ index, speaker, voice_instructions }`, where `index` is the item's position in the paragraph's item list as the prompt numbered it. Text and type are never answered — the model cannot restate book text, so it cannot corrupt it. The wire strings live in one place, `AttributionWire`: reserved speakers `narrator` and `unknown` (an item whose speaker is not known), plus the `narration` / `dialog` labels the prompt uses to describe items it must not answer for.
  _Avoid_: "segment" (the retired name for a model-supplied slice), "chunk" for a piece *of a paragraph* (a chunk is a set of whole paragraphs — see below), "line", treating a paragraph as having one speaker
- **Chunk** — the set of whole paragraphs a chain step asks about in one LLM call: a single-chapter group cut into runs of the config's `AttributionBatchSize`. It is the unit of the step's pipeline, and **a single paragraph is a chunk of 1** — there is no separate single-paragraph path. Only the ask shape varies with size: one included paragraph gets the object-shaped prompt, more than one the array-shaped batch prompt. A chunk is also the unit of failure — an unparseable answer fails the whole chunk, because escalation's unit is the paragraph and a half-answered chunk is not one.
- **Candidate speaker** — a roster Character the visible text has actually placed in the scene, by naming them or by a description that can only be that one person. The known-characters list is the whole *book*, so a listed name is **not** a candidate until the text puts them here; a speaker the text has introduced but not yet identified ("a man", "the stranger") is `unknown`, even though a later chapter names them. The `Full` attribution templates say this outright and add that a wrong name is worse than `unknown` — measured: it converted a cold-start block of confabulations to abstentions with no loss of correct attributions (`.scratch/attribution-abstention/spec.md`). Reaching a name by elimination or best fit is the defect this rules out.
  _Avoid_: treating the roster as a cast list for the current scene, "the model should always pick someone"
- **Fully attributed** — every Character item of a paragraph carries a Character. A paragraph with some stamped and some unstamped Character items is **partly attributed**: still queue-eligible, and never fed to the LLM as context (its unattributed items would poison the surrounding speakers).
- **Attribution outcome** — an answer carries item attributions and applies whether or not every item in it was named: the items it did attribute are real work. Indices it skipped, and indices matching no item, are ignored rather than failing the answer; the items they would have stamped simply stay unattributed. Whether the paragraph is done is decided *after* apply, from the items (an `unknown` on an already-stamped item leaves nothing unattributed), not from the LLM's own confidence.
- **Narrator link** — a project-level pointer, `Projects.NarratorCharacterId`, naming the Character who narrates the book (Sherlock Holmes narrated by Dr. Watson). Null = **unlinked** = every prompt, query and rendered string byte-for-byte as it was before the feature. Read only through **`NarratorIdentity`** (`Read2Me.Data`) — the read-time projection `(CharacterId, DisplayName, IsLinked)`, `Unlinked` being the seed Narrator id + `"Narrator"`. A dangling pointer (no such Character) projects as `Unlinked` rather than failing. Narration items keep stamping `ProjectDbContext.NarratorId` at write time forever — resolution is read-time projection, **never a restamp** — so unlinking is one nulled column with nothing stranded (see [ADR 0004](../docs/adr/0004-narrator-identity-read-time-projection.md)).
  _Avoid_: "narrator mode" (that is `NarratorOnlyMode`, unrelated), restamping narration items to the linked Character
- **Linked character** — the Character the narrator link points at. An ordinary Character in every respect (`IsNarrator = false`, its own Voices and Voice Rules, listed in the roster under its own name); it just also narrates. The always-present **seed Narrator row** (`ProjectDbContext.NarratorId`, `IsNarrator = true`) survives linking — the link is a pointer, not a merge.
- **`narrator` as a wire alias** — reader-side tolerance only, **never advertised**: the roster JSON offers no `"narrator"` alias and no `is_narrator` field, and the seed Narrator row stays listed under the literal name `"Narrator"`. Linked, a `narrator` speaker on a dialog item canonicalizes to the linked character (`ResolveSpeakerAsync`, `CharacterNames.IsKnown`/`Canonicalize`, so `DeriveTrigger` and `AnswersAgree` agree with an answer naming that character). **Unlinked, `narrator` on a dialog item means `unknown`** — null stamp plus `EscalationTrigger.Unknown` — because a spoken line credited to someone by definition not in the scene is not certainty. (Narration items are unaffected: they are stamped with the narrator at import, and answers on their indices are ignored.)
- **Chain entry / chain rung** — one step of the escalation chain as stored: `AttributionChainEntry(ConfigId, Thinking)`. A rung is identified by the **(config, thinking) pair**, not the config alone, so the same config may sit in the chain twice — once fast, once with model thinking on. Resolved for consumers as `ResolvedChainStep(Config, Thinking)`. Thinking is off everywhere it is not explicitly opted in: migrated legacy chains and the empty-chain fallback. The settings UI offers every config in both modes and picks the mode at add time — a rung's thinking flag is immutable afterwards, so switching modes means removing the rung and adding the other variant.
- **Escalation chain** — the ordered list of chain rungs a suspect attribution answer re-asks against. Walked once by `AttributionEscalationChain`: a non-`None` escalation trigger (unknown speaker, unlisted name, parse failure, self-consistency disagreement) re-asks the item on the next config; the best usable answer seen so far survives a last-entry infra failure; the final config accepts an unlisted name as a new Character. A `ModelLoading` outcome short-circuits the walk — escalating would autoload a different model and evict the one still loading. The walk is config-order-agnostic about *how* a config runs (chunk size, self-consistency, final-rung re-ask): that is the **chain step** (`IChainStep`), which runs one config across a set of items, chunk by chunk, and streams back each item's outcome. A single-config chain never escalates and is byte-identical to a plain attribution run.
  _Avoid_: "retry" (a retry re-asks the *same* config; escalation moves to the *next*), conflating the chain (policy) with the step (per-config execution).
