# Character attribution

Use these terms exactly in code, tests, and discussion.

- **Character attribution** — deciding which Character speaks a given Character ParagraphItem, via the LLM. A paragraph with unattributed Character items is **unprocessed**; once a Character is assigned it is **processed**.
- **Character Queue** — the background pipeline. User adds paragraphs; `CharacterQueueWorker` drains it, calling `CharacterAttributionService` per paragraph. `CharacterQueueService` holds queue state keyed by `(folder, paragraphId)`.
- **Segment** — one narration-or-dialog slice of a paragraph as the LLM answers it: `{ text, type, speaker, voice_instructions }`. Attribution asks for a paragraph's whole segment list (re-segmentation is in scope — the imported item split may be wrong), and the answer is reconciled against the existing ParagraphItems. The wire strings live in one place, `SegmentWire`: types `narration` / `dialog`, reserved speakers `narrator` (every narration segment) and `unknown` (a dialog segment whose speaker is not known).
  _Avoid_: "chunk", "line", treating a paragraph as having one speaker
- **Fully attributed** — every Character item of a paragraph carries a Character. A paragraph with some stamped and some unstamped Character items is **partly attributed**: still queue-eligible, and never fed to the LLM as context (its unknown segments would poison the surrounding speakers).
- **Attribution outcome** — an answer carries the segment list, already re-sliced from the original paragraph text, and applies whether or not every speaker in it was named: the segments it did attribute are real work. Whether the paragraph is done is decided *after* apply, from the items (an unknown segment that matched an already-stamped item leaves nothing unattributed), not from the LLM's own confidence.
- **Chain entry / chain rung** — one step of the escalation chain as stored: `AttributionChainEntry(ConfigId, Thinking)`. A rung is identified by the **(config, thinking) pair**, not the config alone, so the same config may sit in the chain twice — once fast, once with model thinking on. Resolved for consumers as `ResolvedChainStep(Config, Thinking)`. Thinking is off everywhere it is not explicitly opted in: new entries, migrated legacy chains, and the empty-chain fallback.
- **Escalation chain** — the ordered list of chain rungs a suspect attribution answer re-asks against. Walked once by `AttributionEscalationChain`: a non-`None` escalation trigger (unknown speaker, unlisted name, parse failure, self-consistency disagreement) re-asks the item on the next config; the best usable answer seen so far survives a last-entry infra failure; the final config accepts an unlisted name as a new Character. A `ModelLoading` outcome short-circuits the walk — escalating would autoload a different model and evict the one still loading. The walk is config-order-agnostic about *how* a config runs (single, batched, self-consistent): that is the **chain step** (`IChainStep`), which runs one config across a set of items and streams back each item's outcome. A single-config chain never escalates and is byte-identical to a plain attribution run.
  _Avoid_: "retry" (a retry re-asks the *same* config; escalation moves to the *next*), conflating the chain (policy) with the step (per-config execution).
