# Character attribution

Use these terms exactly in code, tests, and discussion.

- **Character attribution** — deciding which Character speaks a given speech ParagraphItem, via the LLM. A paragraph with unattributed items is **unprocessed**; once a Character is assigned it is **processed**.
- **Unattributed** — `CharacterId is null`, with no type qualifier: there is no item type to qualify it with any more, and no such thing as "unattributed narration" — the splitter deciding a segment is narration *is* its attribution, so narration carries the narrator sentinel from import ([ADR 0006](../docs/adr/0006-narration-is-a-speaker-not-an-item-type.md)). Unattributed is therefore exactly "dialog nobody has named yet", and it is the queue's unit of work.
- **What the queue asks about** — every **non-narrator** item of the paragraphs it is given: null-speaker items and character-stamped ones alike, the latter re-asked exactly as before when the user requests a re-run. Narrator-stamped items are skipped (they are the narration the model must not answer for, and they still go to it as labelled context). Two user gestures fall out of that rule: assigning an item to the narrator is also what **locks it out of re-attribution**, and clearing its speaker puts it **back in the queue as unattributed dialog**. There is no other per-item "manually set" protection.
- **Character Queue** — the background pipeline. User adds paragraphs; `CharacterQueueWorker` drains it, calling `CharacterAttributionService` per paragraph. `CharacterQueueService` holds queue state keyed by `(folder, paragraphId)`.
- **Frozen boundaries** — the rule that a paragraph's ParagraphItems are set by the deterministic import-time split (`ParagraphSplitter`, a quote scan) and only a user may change them. Attribution never re-slices, never creates and never deletes an item; the LLM sees the split as given and answers only who speaks each one ([ADR 0005](../docs/adr/0005-frozen-paragraph-item-boundaries.md)). An item that genuinely holds two speakers is therefore unanswerable, and its speaker is `unknown` by rule — a signal for the user to repair the split, not a case for the model to fix.
  _Avoid_: "re-segmentation", "the model splits the paragraph" (both describe the retired design)
- **Item attribution** — the LLM's answer about one ParagraphItem: `{ index, speaker, voice_instructions }`, where `index` is the item's position in the paragraph's item list as the prompt numbered it. Text and type are never answered — the model cannot restate book text, so it cannot corrupt it. The wire strings live in one place, `AttributionWire`: reserved speakers `narrator` and `unknown` (an item whose speaker is not known), plus the `narration` / `dialog` labels the prompt uses to describe items it must not answer for.
  _Avoid_: "segment" (the retired name for a model-supplied slice) — one exception, deliberate: `"segments"` survives as the JSON key naming a **context** paragraph's items in the prompt, because renaming a wire key rewrites all four prompts for a word; "chunk" for a piece *of a paragraph* (a chunk is a set of whole paragraphs — see below), "line", treating a paragraph as having one speaker
- **Chunk** — the set of whole paragraphs a chain step asks about in one LLM call: a single-chapter group cut into runs of the config's `AttributionBatchSize`. It is the unit of the step's pipeline, and **a single paragraph is a chunk of 1** — there is no separate single-paragraph path. Only the ask shape varies with size: one included paragraph gets the object-shaped prompt, more than one the array-shaped batch prompt. A chunk is also the unit of failure — an unparseable answer fails the whole chunk, because escalation's unit is the paragraph and a half-answered chunk is not one. A Chapter rung has no chunks: it asks one item per call, and its unit of failure on an infra outcome (`Failed`, `ServiceUnavailable`, `ModelLoading`) is **the rest of the chapter** — the current paragraph and every queued paragraph after it get the same outcome. A parse failure fails only its own paragraph.
- **Candidate speaker** — a roster Character the visible text has actually placed in the scene, by naming them or by a description that can only be that one person. The known-characters list is the whole *book*, so a listed name is **not** a candidate until the text puts them here; a speaker the text has introduced but not yet identified ("a man", "the stranger") is `unknown`, even though a later chapter names them. The `Full` attribution templates say this outright and add that a wrong name is worse than `unknown` — measured: it converted a cold-start block of confabulations to abstentions with no loss of correct attributions (`.scratch/attribution-abstention/spec.md`). Reaching a name by elimination or best fit is the defect this rules out.
  _Avoid_: treating the roster as a cast list for the current scene, "the model should always pick someone"
- **Fully attributed** — every non-narrator item of a paragraph carries a Character. A paragraph with some stamped and some unstamped items is **partly attributed**: still queue-eligible, and never fed to the LLM as context on the `Full` and `Simple` paths (its unattributed items would poison the surrounding speakers). The chapter pass deliberately diverges: it renders the whole chapter, with unstamped items shown unlabelled, because that is the layout the spike measured ([ADR 0013](../docs/adr/0013-chapter-pass-attribution-opt-in.md)).
- **Attribution outcome** — an answer carries item attributions and applies whether or not every item in it was named: the items it did attribute are real work. Indices it skipped, and indices matching no item, are ignored rather than failing the answer; the items they would have stamped simply stay unattributed. Whether the paragraph is done is decided *after* apply, from the items (an `unknown` on an already-stamped item leaves nothing unattributed), not from the LLM's own confidence.
- **Narrator link** — a project-level pointer, `Projects.NarratorCharacterId`, naming the Character who narrates the book (Sherlock Holmes narrated by Dr. Watson). Null = **unlinked** = every prompt, query and rendered string byte-for-byte as it was before the feature. Read only through **`NarratorIdentity`** (`Read2Me.Data`) — the read-time projection `(CharacterId, DisplayName, IsLinked)`, `Unlinked` being the seed Narrator id + `"Narrator"`. A dangling pointer (no such Character) projects as `Unlinked` rather than failing. Narration items keep stamping `ProjectDbContext.NarratorId` at write time forever — resolution is read-time projection, **never a restamp** — so unlinking is one nulled column with nothing stranded (see [ADR 0004](../docs/adr/0004-narrator-identity-read-time-projection.md)).
  _Avoid_: "narrator mode" (that is `NarratorOnlyMode`, unrelated), restamping narration items to the linked Character
- **Linked character** — the Character the narrator link points at. An ordinary Character in every respect (`IsNarrator = false`, its own Voices and Voice Rules, listed in the roster under its own name); it just also narrates. The always-present **seed Narrator row** (`ProjectDbContext.NarratorId`, `IsNarrator = true`) survives linking — the link is a pointer, not a merge.
- **`narrator` as a wire alias** — reader-side tolerance only, **never advertised**: the roster JSON offers no `"narrator"` alias and no `is_narrator` field, and the seed Narrator row stays listed under the literal name `"Narrator"`. Linked, a `narrator` speaker on a dialog item canonicalizes to the linked character (`ResolveSpeakerAsync`, `CharacterNames.IsKnown`/`Canonicalize`, so `DeriveTrigger` and `AnswersAgree` agree with an answer naming that character). **Unlinked, `narrator` on a dialog item means `unknown`** — null stamp plus `EscalationTrigger.Unknown` — because a spoken line credited to someone by definition not in the scene is not certainty. (Narration items are unaffected: they are stamped with the narrator at import, and answers on their indices are ignored.)
- **Chain entry / chain rung** — one step of the escalation chain as stored: `AttributionChainEntry(ConfigId, Thinking, Style)`. A rung is identified by the **(config, thinking, prompt style) triple**, not the config alone, so the same config may sit in the chain up to five times — fast or with model thinking on, each under the Full or the Simple prompt, plus fast under the Chapter prompt style (a chapter pass always runs with thinking off, so there is no thinking Chapter variant). A stored style of null inherits the config's own. Resolved for consumers as `ResolvedChainStep(Config, Thinking, Style)` with the effective style. Over HTTP (`/api/settings/llm/attribution-chain`) the stored rungs travel as `steps`. Thinking is off everywhere it is not explicitly opted in: migrated legacy chains and the empty-chain fallback. The settings page offers every config in all five variants and picks the variant at add time — a rung's flags are immutable afterwards, so switching modes means removing the rung and adding the other variant.
- **Chapter prompt style** — `AttributionPromptStyle.Chapter`, the opt-in third style beside `Full` and `Simple`, chosen on an LLM config or one chain rung. `StyleRoutedChainStep` sends a Chapter rung to `ChapterAttributionStep` (the chapter pass) and every other rung to `CharacterAttributionService`, which is unchanged. Thinking off, temperature 0 and `max_tokens` 48 are forced whatever the config says; self-consistency and the final-rung re-ask do not apply. Meant for the `gemma-12b` preset ([ADR 0013](../docs/adr/0013-chapter-pass-attribution-opt-in.md)); `Full` stays the default.
- **Chapter pass** — what a Chapter rung does with its queued paragraphs: grouped by chapter in book order, each chapter is walked one dialog item per LLM call, in order. The prompt shows the whole chapter so far plus 4 look-ahead paragraphs, with earlier answers (and rule tags) shown inline as `{Name}` labels, so each answer feeds the next. Per chapter it runs rules-discover, reads the roster, snapshots the chapter once, runs the rules pre-tag, then asks. **Cache contract:** the system message (instructions, book, roster) is built once per chapter; the user message is append-only between calls — the only change to an earlier line is a `{Name}` inserted for an item just answered, and nothing per-call (counters, ids, timestamps) precedes the passage — so llama reuses the prefix and prefills only the new tail. The pass renders from its snapshot and never re-reads the chapter mid-pass. A chapter over the prompt budget is front-trimmed by halves, and the trim point then stays fixed. Partly attributed paragraphs are rendered as context (see Fully attributed).
  _Avoid_: "chapter mode", "whole-chapter batch" — it is one item per call, not one call per chapter.
- **Roster grammar** — the GBNF grammar a chapter-pass call is constrained by (`RosterGrammar`): `Name | delivery`, where Name is exactly one roster name or `Unknown`, and delivery is an optional cue of up to 40 characters. The seed Narrator row and any Character literally named `Unknown` are left out. Because the answer cannot name anyone off the list, **the model never creates a Character on this path** — only rules-discover does. A rule-tagged item gets a **voice-only call**: the same prompt under a grammar that admits only the tagged name, so only the delivery is asked.
- **`Unknown` answer** — the chapter pass's abstention: the grammar's one non-roster name. It maps to `AttributionWire.Unknown` (null stamp), drops its delivery, sets no label, and makes the paragraph suspect with `EscalationTrigger.Unknown`, so the walk re-asks it on the next rung after the whole step-0 pass — or leaves it for manual review in a one-rung chain.
- **Speech-tag rules / rule tag** — `SpeechTagRules` (`Characters/Rules/`), a deterministic C# port of the spike's said-tag tagger. **Rules pre-tag** (`TagChapter`) reads explicit speech tags ("…," said Pug) against the roster and its aliases and yields a **rule tag** per item it can name with certainty: item → (name, rule id, e.g. `T1-post-vs`). A rule tag is shown as a label from the first call, and a tagged item in a queued paragraph gets a voice-only call with its name fixed. An already stamped item in a non-queued paragraph keeps its stamp over a tag.
- **Rules-discover** — `SpeechTagRules.DiscoverNames`, run before each chapter of a chapter pass: the said-tags whose named speaker is not on the roster (after dropping openers, `-ly` words, honorific-only and roster-word-sharing mentions) become new Characters through `CharacterResolver`, without asking. It is the **only creator** on the Chapter path. Each creation is logged with its count and an example tag; a phantom (a place or an opener the filters missed) is merged by the user in the cast list.
- **Delivery cue** — the `| delivery` half of a chapter-pass answer, stored as the item's `VoiceInstructions`: a short volume-and-manner cue for TTS. It must agree with an explicit manner tag ("softly", "whispered"), names no sound actions or gestures ("chuckling", "smiling"), is at most 40 characters, and may be `plain` for a neutral line, which maps to no instruction (null), as does an empty cue.
  _Avoid_: "voice", "emotion" — a Voice is the audio reference (`context/voice-rules.md`).
- **Escalation chain** — the ordered list of chain rungs a suspect attribution answer re-asks against. Walked once by `AttributionEscalationChain`: a non-`None` escalation trigger (unknown speaker, unlisted name, parse failure, self-consistency disagreement) re-asks the item on the next config; the best usable answer seen so far survives a last-entry infra failure; the final config accepts an unlisted name as a new Character. A `ModelLoading` outcome short-circuits the walk — escalating would autoload a different model and evict the one still loading. The walk is config-order-agnostic about *how* a config runs (chunk size, self-consistency, final-rung re-ask): that is the **chain step** (`IChainStep`), which runs one config across a set of items, chunk by chunk, and streams back each item's outcome. A single-config chain never escalates and is byte-identical to a plain attribution run.
  _Avoid_: "retry" (a retry re-asks the *same* config; escalation moves to the *next*), conflating the chain (policy) with the step (per-config execution).
