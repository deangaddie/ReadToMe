# Browser tests

Keep them to a minimum; the aim is none. The rules, in short:

- A browser test is only for layout or scroll, the real top layer, or the real hub.
- The real hub is proven once, by `LiveUpdateTests`. A feature's hub signal reaching its page is a web spec over `FakeLive`, not another browser test.
- Every browser test carries a one-line comment above its `[Fact]`, `// Needs a real browser: <why>.` A test that cannot say it belongs in a bun spec or a host test.
- Logic a failing browser test holds (anchoring maths, reconnect and refetch, state after a click) moves to a bun spec; the browser test shrinks to what only a real engine proves.

The repeat Firefox failures (`BigBookTests` deep link, `NodeMenuTests` anchor, `LiveUpdateTests` reconnect) were reshaped this way (#265): the anchoring maths is in `reader-anchoring.spec.ts` (the real list and `ReaderWindow` over fake geometry), the anchor surviving a re-render in `book-page.spec.ts`, and the reconnect, re-join and refetch in `live-reconnect.spec.ts` (the real `LiveService` and `BookStore` over a fake socket); each browser test keeps one real-engine case.

A browser test earns its place only when nothing cheaper can prove the behaviour: real layout and scrolling (happy-dom has no layout), the real top layer (popover anchoring, focus through a real modal), or the bundle's SignalR client against the real hub. A flow whose layers each have a cheaper test does not get one: a web spec over `FakeApi`/`FakeLive` covers the web side, an API or unit test covers the host side, and the regenerated contract (`openapi.json` → `schema.d.ts`, then typecheck; the hub's messages are in it too) catches drift between them. Every browser test runs in both browsers and is the likeliest place for a timing race. On 2026-10-13 the suite was cut from 68 tests to a handful, and each class stays for one of those reasons: `LiveUpdateTests` (after a forced hub disconnect, a split posted to the API reaches the open page through its receipt), `BigBookTests` (a deep link holds its header over prepends; a row menu deep in the list opens on its trigger; anchoring holds over a resize), `NodeMenuTests` (a menu stays on its trigger while a receipt re-renders the tree; focus returns to the tree item through the real confirm), `HistorySheetTests` (the History sheet docks beside the page and covers the page body under 900 px; the viewing banner sits between the app bar and a greyed page), `OverviewLayoutTests` (at phone width the stepper leads, help opens inline under a split head row, and the next-step pill keeps only its main button under 900 px), `RowHighlightTests` (a row's hover highlight holds while pointer and focus are in its open menu's top-layer popover; computed styles need a real engine) and `PronunciationMarksTests` (the Book view's hover card is a top-layer popover over the reader under its mark), `PronunciationPanelTests` (the panel is a third column on a wide page and floats over the reader's right edge on a narrow one; dragging the structure tree wider floats it, keeps the reader at least 450 px, and the width survives a reload), `SetupCheckSurfacingTests` (the start banner sits between the app bar and the body, and the failed count sits on the shield), `ProjectsSeriesLayoutTests` (an open series' panel spans the Series grid directly after the last card in the clicked card's row) and `SeriesVoiceEditorTests` (two rows' series Voice editors open at once, each directly under its row).

`E2eTestBase` (in `src/Read2Me.E2eTests/Infrastructure`) copies the built bundle into the in-proc host's web root; `GotoAppAsync("projects/x/book")` adds the `/app` prefix and waits until the shell reports the live hub connected (`data-live-state="connected"` on `app-root`, so a transport fallback still counts), and `AppPath(...)` builds the expected URL. `R2M_E2E_BROWSER=chromium|firefox` picks the browser, and every class runs in both. Each test class gets its own host, an `E2eAppFixture` class fixture (`E2eTestBase` declares it; an API or host class adds `IClassFixture<E2eAppFixture>` itself): `FakeAi` (LLM/TTS/whisper replies), `FakeControl` (container statuses, op log), `Encoder` (fake ffmpeg), the seeders (`SeedProjectAsync`, `SeedThreeDialogParagraphProjectAsync`, …) and `WaitForQueueDrainAsync`. Classes run in parallel and share only the browser (`PlaywrightFixture`); don't put a class in a `[Collection]`, which would serialize it and share its host again. Tests inside a class run in order on that host, so host state a test changes (a shut-down fake service, a theme selection, an active config) must still be restored in a `finally` for the class's next test; the fakes are reset before every browser test.

Classes in parallel make every browser slow at times (a single Firefox click can take seconds), so a test waits on a signal, never on time. To catch work in flight, hold it rather than slow it: `FakeAi.HoldLlmAfter(n)` answers `n` completions and holds the rest until their request is cancelled or `FakeAi.ReleaseLlm()`, which a fixed delay would only make likely. Watch for something short-lived (a 3 s toast) from before the action that causes it (`locator.WaitForAsync()` started early, awaited at the end), and press keys that must land together (type-ahead's 200 ms window) in one in-page burst rather than with `Keyboard.TypeAsync`, which waits a round trip per key. An API test that opens the live hub with a `HubConnection` and expects a push before it invokes any hub method starts it with `StartJoinedAsync()`: `StartAsync` returns before the hub has joined the connection to its groups, so a push right after it can be lost (a hub invocation such as `JoinProject` is the same round trip).

One file per area under `Tests/Web`, named for what it proves. Locate by `r2m-*` element or BEM class, `data-action` / `data-entry` / `data-testid`, or ARIA roles and labels. Partials put their name on their root as a class (`.r2m-job-pill`), drawer tabs are `GetByRole(AriaRole.Tab, new() { Name = "LLM" })`, the preflight sheet sits inside `GetByRole(AriaRole.Dialog)`, and a select is a native `<select>`: locate it with `GetByRole(AriaRole.Combobox)`, pick with `SelectOptionAsync(new SelectOptionValue { Label = "…" })`, and read its choices from `option:not([disabled])` (a placeholder option is disabled and hidden). An expansion panel opens by clicking its `summary` (`card.Locator("[data-section='advanced'] > summary")`), and an element that marks `aria-busy="true"` during a write is awaited with `Expect(card).Not.ToHaveAttributeAsync("aria-busy", "true")` before the next assertion. A popover menu's `role=menu` carries the same `aria-label` as the button that opens it, so locate the trigger by role (`GetByRole(AriaRole.Button, new() { Name = "Actions for x" })`, not `[aria-label=…]`) and its entries as `GetByRole(AriaRole.Menuitem, …)`; a toggle is a checkbox `role=switch`, asserted with `ToBeCheckedAsync()`. A test that needs background work queues it through the agent API (`…/attribution/enqueue-paragraphs`), not through the UI.
