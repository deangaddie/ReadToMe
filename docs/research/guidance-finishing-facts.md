# What the title sweeps, pause planner, assembly gates and project metadata give the Titles, Pauses and Export rows

Research for the Finishing guidance map (`.scratch/guidance-finishing`), resolved 2026-10-17 against the repo at `00e6b25`. Every claim carries a `file:line` pointer relative to the repo root. Vocabulary follows `context/assembly.md`, `context/book-structure.md` and `context/web.md`.

Four things the map's "Facts today" or charting assumptions got wrong, up front:

- **The Audio Queue in-flight gate does not exist in code.** `context/assembly.md:8` says Assemble is disabled while the queue has in-flight items for the project; neither the Assemble button nor the start endpoint nor the service checks the queue (§5). Assumption (e)/(f) are unaffected, but the glossary line is stale.
- **The Export step reads the newest file by mtime, whatever its kind.** `lastBuild` is `outputs[0]` of a list ordered by `LastWriteTimeUtc` descending; a partial build made after a full one turns the Export step back to `notStarted` even though the full build still exists (§5). Assumption (f)'s "partial leaves the step open" is true only because of this ordering, not because of a per-kind rule.
- **The web app cannot edit `BookTitle` after creation.** The details panel edits the project `Title` and `Author`; `Book title` is a read-only key-value row (§3, §8). `AddBookTitle` narrates `BookTitle`, and the m4b `title`/`album` tags and file name are `BookTitle` too. Assumption (c) ("title and author must be set before Add titles, surfaced on the Titles row") has no title field to point at today.
- **Pause entries are offered on pause items too, and every title sweep stacks on re-run.** The Node menu adds the five Pause before / after entries for every `item` anchor, pause or speech, and the host accepts any item (§4). None of the four title sweeps skips: a second `AddBookTitle` creates another Volume, Part or Chapter in front of the previous one (§1).

## 1. Title sweeps

**Shared staging.** All four sweeps answer `StructuralAdditionEffects.Swept` = `{ Scope = WholeProject, Facets = BookFacets.Structure }` — `src/Read2Me.Services/Mutations/Implementations/StructuralAdditionMutationImplementations.cs:23-27`. `BookFacets` is a flags enum (`src/Read2Me.Services/Mutations/BookMutationEffects.cs:21-48`); `NodeTitle` (`:45`) is emitted only by the retitle paths (`BookEditMutationImplementations.cs:70`, `:299`), never by a title sweep. So a sweep's receipt carries exactly `Structure`, no `ItemText`, no `NodeTitle`.

**What each inserts.** `TitleInserter.AddParagraph` creates one `Paragraph` with a fresh `Order` and one `ParagraphItem` of `ItemType = Speech`, `CharacterId = ProjectDbContext.NarratorId`, `Text = text` — `src/Read2Me.Services/Books/TitleInserter.cs:20-41`. There is no flag, no item type and no column that distinguishes it from a narrated body paragraph (`src/Read2Me.Data/Entities/ParagraphItem.cs:17-30`; `Paragraph.cs:3-11`).

- **`AddBookTitle`** (`StructuralAdditionMutationImplementations.cs:47-66`): reads the single `Project` row (`:52`), plans front matter (`BookHierarchy.PlanFrontMatterInsert`, `src/Read2Me.Services/Books/BookHierarchy.cs:517-592`), stages it, then inserts `project.BookTitle` first and `$"By {project.Author}"` after it (`:62-63`). Front matter is a **new** container every run: with more than one Volume a new Volume (`Title = string.Empty`) + Part + Chapter before the first Volume (`BookHierarchy.cs:523-546`); with one Volume and several Parts a new Part + Chapter before the first Part (`:548-570`); otherwise a new Chapter before the first Chapter of the first Part (`:571-586`). `null` (→ `Nothing`) only when there are no Volumes or the one Volume has no Parts (`:519`, `:574`). The new Chapter's `Title` is never set (null).
- **`AddVolumeTitles` / `AddPartTitles`** (`:68-86`): per node with a non-blank title, a new Chapter with `Title` null, ordered before the first Chapter of the node's first Part (`BookHierarchy.cs:600-642`), holding one title paragraph (`StageTitleChapters`, `:33-44`). A Volume with no Parts is skipped (`:607`). The title text is the node's `Title` as stored, untrimmed.
- **`AddChapterTitles`** (`:88-101`): per Chapter with a non-blank title, one title paragraph ordered before its first paragraph (`BookHierarchy.cs:644-658`; `firstParagraph?.Order` null → first).
- **Blank title**: `string.IsNullOrWhiteSpace(…) → continue` at `BookHierarchy.cs:605`, `:629`, `:651` — skipped silently; a book whose nodes are all untitled answers `Nothing`.

**Second run.** No planner looks at existing paragraphs or chapters: `PlanVolumeTitleChapters` and `PlanPartTitleChapters` compute `GetBefore(firstChapter?.Order)` where `firstChapter` is now the previous title chapter, so a second title chapter lands in front of the first; `PlanChapterTitleInsertions` inserts before the previous title paragraph; `PlanFrontMatterInsert` creates another front-matter node. Duplicate narration every time, never a skip. Contrast `AddPauses`, whose planner skips what exists (`:110`).

**`Nothing` on the wire.** A sweep that adds nothing rolls back without a revision or receipt (`src/Read2Me.Services/Mutations/BookMutations.cs:122-128`) and the command endpoint answers `200 { newEntityId: null }` exactly as for a commit (`src/Read2Me.App/Api/BookCommandApiAdapter.cs:46-51`). The web editor shows nothing on success (`src/Read2Me.Web/src/app/pages/book/book-editor.ts:19-22`), arms a 2 s own-receipt wait (`:16`, `:107`) and, no receipt arriving, falls back to `store.refresh()` (`:116`). A user cannot tell "nothing to add" from "added".

**Tree, Book page, chapter markers.** The new title chapter has a null title, so the tree and the Book page heading show the Placeholder title `Untitled chapter N` in the muted style (`src/Read2Me.Web/src/app/pages/book/book-tree.ts:57-61`, `book-page.ts:597`; glossary `context/book-structure.md:27`). In the manifest it is a section of its own, so `ComputeChapterTimestamps` emits a marker at its first audio item labelled `entry.ChapterTitle ?? $"Chapter {chapIdx}"` (`src/Read2Me.Services/Audio/AudiobookAssemblyPlanner.cs:153`): a title chapter at the front of a Part is marker "Chapter 1", and the first real chapter keeps its own title. Because the title chapter is also the first item of its Volume and Part, the Volume and Part markers land at the same offset (`:148-151`), flat and sharing one `End` (`:179-191`). The `AddBookTitle` front-matter Volume has `Title = ""` (not null), so its marker title is the empty string; its Part has a null title and takes the fallback `Chapter {partIdx}` — the fallback word is "Chapter" at every level (`:149-151`).

**The toolbar entries.** `TITLE_ACTIONS` (`src/Read2Me.Web/src/app/pages/book/book-page.ts:77-114`) is filtered by `titleActions` (`:199-205`): `volumes > 1`, `parts > volumes`, `chapters > parts`, from `overview.volumes.length`, `overview.totalParts`, `overview.totalChapters` (`BookEndpoints.cs:66-67`). Add book title always shows. Add pauses sits after a divider (`:522`). The whole menu is disabled while the editor is locked or the overview is missing (`:514`).

*What this means for assumption (b):* confirmed — no title sweep skips. *For (d):* confirmed, with a sharper edge: the title chapter reads `Untitled chapter 1` in the tree and lands as an m4b marker called "Chapter 1", plus stacked Volume/Part markers at the same offset; the front-matter Volume from `AddBookTitle` produces an empty-string marker.

## 2. Title marker feasibility

**Where a marker could live.** `ParagraphItem` has `Id, ParagraphId, Order, ItemType, Text, CharacterId, VoiceInstructions, AudioFileName` (`src/Read2Me.Data/Entities/ParagraphItem.cs:19-26`); `Paragraph` has `Id, ChapterId, Order` (`Paragraph.cs:5-7`). `ParagraphItemType` is `Speech` plus five pause kinds (`src/Read2Me.Data/Enums/ParagraphItemType.cs:11-19`) and `ParagraphItemKinds` is documented as the one place that still reads it, deciding only pause-or-spoken (`src/Read2Me.Data/ParagraphItemKinds.cs:7-11`); the speech-vs-pause test is an EF expression `ItemType == Speech` (`:37-38`) used by the status seed (`ProjectReader.Audio.cs:129`) and the manifest's null-audio rule (`:206-212`). A new item type would therefore have to be added to every `IsSpeech`/`IsPause` site or the type would be excluded from counts; a nullable column on `ParagraphItem` (or `Paragraph`) is the shape that touches none of them.

**Reads that would need it.**

- Double-insertion refusal: each planner (`BookHierarchy.cs:600-658`, `:517-592`) would test "the node already holds a marked paragraph" before planning; `BookHierarchy` already indexes `Items` per paragraph (`:736-741`), so it is a dictionary lookup, no extra query.
- Per-level "titles present" counts: the status path has no title count today (`ProjectStatusDto`, `src/Read2Me.App/Api/ProjectStatusEndpoints.cs:26-37`); a count of marked items grouped by level is one `GroupBy` over `ParagraphItems` with the marker predicate, alongside `GetNodeStatusSeedAsync` (`ProjectReader.Audio.cs:123-146`).
- Re-insert after re-read: every row is deleted by `BookContentRemoval` (`ExecuteDeleteAsync` over items, paragraphs, chapters, parts, volumes — `DestructiveStructuralMutationImplementations.cs:294-298`), so a marker cannot survive a reread; only the planner's idempotence matters afterwards.
- Re-narrate after `Edit title` or project rename: `RetitleOneAsync` updates the node title and emits `NodeTitle` (`BookEditMutationImplementations.cs:62-72`); a marked paragraph under that node could be found by `ChapterId`/level and its `Text` rewritten plus `AudioFileName` cleared. Project rename does not go through mutations at all (`ProjectService.UpdateMetadataAsync`, `src/Read2Me.Services/ProjectService.cs:101-113`), so a book-title re-narration would need a new seam there.

**Migration path.** Per-project SQLite databases migrate on open (`src/Read2Me.Services/ProjectDbContextFactory.cs:18`, `db.Database.MigrateAsync()`; app-level `Program.cs:49`), with EF migrations under `src/Read2Me.Data/Migrations/` (latest `20260831131907_CollapseSpeechItemType`). A nullable column migration backfills nothing; existing projects' inserted titles stay unmarked unless a one-off heuristic backfill is written.

**Cost of a text-match heuristic.** The only signal available is "the first speech paragraph of the chapter has `Text == chapter.Title` and `CharacterId == NarratorId`" (and for Volume/Part title chapters, "an untitled chapter whose only paragraph equals the parent's title"). It needs the node title at check time, fails after `Edit title` (the narration keeps the old name, §3), fails for the `By {Author}` line unless author is also compared, matches a body paragraph that happens to repeat the heading, and gives no per-level count without walking every chapter's first paragraph. `BookHierarchy` already loads all items, so the planner-side check is cheap; the status-path count would be a correlated query per chapter.

## 4. Pauses

**Planner rules** (`BookHierarchy.PlanPauseInsertions`, `src/Read2Me.Services/Books/BookHierarchy.cs:665-732`):

- *Paragraph pauses* (`:669-685`): per chapter, over the content paragraphs (those not `IsPauseParagraph`), for each adjacent pair, plan a `ParagraphPause` between them unless any paragraph strictly between their `Order` keys is a pause paragraph (`:677-682`). So any pause kind between two content paragraphs counts as "has a pause".
- *Boundary pauses* (`:687-729`): walking Volume → Part → Chapter, the last chapter of the last part of a non-last volume gets `VolumePause`; the last chapter of a non-last part gets `PartPause`; a non-last chapter gets `ChapterPause`; the book's final chapter gets none (`:703-710`). Skip only when the chapter's **last** paragraph is a pause paragraph with exactly one item of that **exact** type (`:717-723`); a last paragraph that is a different pause kind (a trailing `ParagraphPause`, say) does not count and a second pause is appended after it (`:725-726`).
- `IsPauseParagraph`: no items, or exactly one item of a pause kind (`:736-741`). An empty paragraph reads as a pause.

**Afterwards.** The planner is pure over the loaded hierarchy and runs only when `AddPauses` is sent; no split, insert, merge or retitle re-plans. A `SplitChapter` leaves the new chapter boundary without a `ChapterPause` and the old chapter's `ChapterPause` now mid-part; an insert at the end of a chapter sits after the boundary pause. `AddPauses` again repairs both, idempotently (`StructuralAdditionMutationImplementations.cs:108-116`; `Nothing` when nothing is planned).

**Cost of a status-path count.** The status path already issues several sequential reads (`ProjectStatusEndpoints.cs:60-63`); `GetNodeStatusSeedAsync` groups speech items per paragraph (`ProjectReader.Audio.cs:128-146`) and knows nothing about pauses. "Chapters lacking a boundary pause" is exactly the planner's second loop; the cheapest host-side form is to load `BookHierarchy` (the same `LoadBookHierarchyAsync` the mutations use) and count `PlanPauseInsertions()` entries by kind: one full-book read, no new query. "Content gaps without a paragraph pause" is the first loop's count. Both come out of one `PlanPauseInsertions()` call, so a signal is `{ boundary: n, paragraph: m }` from one load.

**Node menu entries.** For every `item` anchor the web adds five entries under `pause-before` and five under `pause-after`, labelled Pause, Paragraph pause, Chapter pause, Part pause, Volume pause (`src/Read2Me.Web/src/app/pages/book/node-menu-entries.ts:96-102`, `:278-289`); nothing excludes a pause item (the `isPause` guard at `:267` covers only the insert rule). Each posts `InsertPauseParagraph { anchorItemId, position, pauseKind }` (`node-menu-commands.ts:130-137`). The host creates one pause `Paragraph` with one item of the mapped type beside the anchor's **paragraph** (never inside it), answering `Scope = Exact, Facets = Structure, CreatedId, ParagraphIds` (`StructuralAdditionMutationImplementations.cs:123-178`); it does not check that the anchor is speech (`:141`).

**Durations.** `PauseMs` maps kind → `AppSettings` value (`AudiobookAssemblyPlanner.cs:12-21`); defaults 4000/3000/2500/800/500 (`src/Read2Me.Services/AudioProcessingSettingsService.cs:38-42`); saved together by `PUT /api/settings/audio-processing/pauses` (400 on a negative, `AudioProcessingEndpoints.cs:108-115`); edited on the audio settings page's pauses card (`src/Read2Me.Web/src/app/pages/settings/audio/audio-settings-page.ts:151-157`, `:244-252`), route `settings/audio` (linked from the Export page at `export-page.ts:198`).

*What this means for assumption (e):* confirmed; the signal is one `BookHierarchy` load reusing the planner, not a new query, and "Add pauses again" is indeed idempotent. Note the exact-type skip: a boundary that already holds the *wrong* pause kind is reported as lacking one and gets a second pause.

**Start endpoint** `POST /api/projects/{folder}/assembly` (`src/Read2Me.App/Api/AssemblyEndpoints.cs:87-113`): 404 for an unknown folder; when `allowPartial` is false it counts manifest entries that are not pauses and have no `AudioRelativePath` and answers `409 Problem("{n} items still need audio. **Service.** Single-flight on `IsRunning` under a lock (`src/Read2Me.Services/Audio/Assembly/AudiobookAssemblyService.cs:52-70`); the Gather phase recounts and, without `allowPartial`, stops silently with `AudioRemainingCount` set (`:99-111`, no event). `allowPartial` runs `FilterPartialManifest`: drops speech entries without audio, then collapses each run of adjacent pauses to the highest-level kind by `PauseRank` (`AudiobookAssemblyPlanner.cs:25-66`). **Outputs.** `GET …/assembly/outputs` lists `*.m4b` under `{project}/output/` newest first by `LastWriteTimeUtc`, `isPartial` = name contains `_partial_` (`AssemblyOutputs.cs:27-39`; DTO `AssemblyEndpoints.cs:23`). `GET …/outputs/{fileName}` streams `audio/mp4` as an attachment with range support; `DELETE` answers 204/404 (`:57-72`); the file name must be a bare `.m4b` name that exists (`AssemblyOutputs.TryResolve`, `:45-59`). **`lastBuild`.** The Overview loads `outputs(folder)` and keeps `[newest]` (`overview-page.ts:58-59`, `:141-148`), maps it to `{ date: formatBuildDate(createdAt), isPartial }` (`:67-72`; `formatBuildDate` = day/short month/year, `:29-35`), and reloads on a hub `assembly` message of kind `completed` for this folder (`:94-99`) and on project change (`:85-91`). `derivePipeline` marks Export `running` while `assemblyRunning`, `done` only when `lastBuild && !isPartial`, else `notStarted` (`pipeline-steps.ts:139-143`); detail "Last build: {date}" + " (partial)" (`:270-272`). *What this means for assumption (f):* "Export stays derived-only" and "partial leaves the step open" are confirmed as behaviour, but the mechanism is "newest file by mtime is not partial", which also turns a finished full build back to not-done when a later partial exists. *For the glossary:* the Audio Queue gate line in `context/assembly.md:8` describes nothing in code.

## 6. Stale build

What exists to compare against:

- **Output file mtime**: `AssemblyOutput.CreatedAt` is `LastWriteTimeUtc` of the `.m4b` (`AssemblyOutputs.cs:35-37`), already on the wire.
- **WAV mtime**: item audio is written to `{project}/audio/{itemId}.wav` (`src/Read2Me.Services/Audio/FileAudioPipeline.cs:62-68`); `IFileSystem.ListFiles` returns `FileEntry(Path, LastWriteTimeUtc)` (`src/Read2Me.Core/IO/IFileSystem.cs:4`, `FileSystemService.cs:24-31`), so "newest WAV" is one directory listing; nothing reads it for this purpose today.
- **Database timestamps**: `ParagraphItem`, `Paragraph`, `Chapter`, `Part`, `Volume` and `Project` carry **no** created/updated columns (`src/Read2Me.Data/Entities/*.cs`); only `AudioReview.CreatedUtc/UpdatedUtc` and `Voice.CreatedUtc` exist (`AudioReview.cs:20-21`, `Voice.cs:17`). `RecordParagraphItemAudioMutation` sets `AudioFileName` only (`AudioRecordingMutationImplementations.cs:119`).
- **Revision**: `BookRevisionSequence` is process-local, not persisted, restarts at 1 and answers 0 for a project not mutated in this process (`src/Read2Me.Services/Mutations/BookRevisionSequence.cs:6-10`, `:32-33`); `ProjectStatusDto.Revision` carries it (`ProjectStatusEndpoints.cs:37`, `:59`). It cannot be stored against a build without a schema or file change.
- **Metadata edits** (title, author, cover) leave no mark at all (§3).

So the only comparisons available without new persistence are output mtime against the newest WAV mtime (audio changes) and against the SQLite file's own mtime (any write, including status-free ones). Text and structure changes that clear no WAV are invisible to a WAV comparison.

*What this means for the "Stale-build signal shape" open question:* there is no stored revision to compare; the choices are file mtimes or a new persisted stamp.

## 8. Cover and metadata

**Where editable.** Only the Overview's details panel: cover via `r2m-file-drop` ("Add a cover" / "Replace cover", hint "JPG, PNG or WebP, up to 10 MB", client-side rejections toasted, `:73-95`, `:178-185`), Title and Author inline (`:97-115`); Book title read-only (`:117-123`). ""`, `genre=Audiobook` (`AudiobookAssemblyService.cs:119-121`, `AudiobookAssemblyPlanner.cs:198-209`); an empty author yields empty `artist`/`album_artist` values, an empty book title yields empty `title`/`album` and a file named `.m4b` (`AssemblyOutputs.Sanitize("")`, `AssemblyOutputs.cs:20-21`, `:61-65`). ## Surprises

- `context/assembly.md:8` describes an Audio Queue in-flight gate on Assemble that no code implements; the only gates are content, the global single run and the 409 for missing audio.
- `lastBuild` is the newest `.m4b` by file mtime regardless of kind, so a later partial build un-does the Export step although the full build still exists on disk and in the Outputs list.
- `BookTitle` — what `AddBookTitle` narrates, what names the output file and fills `title`/`album` — has no edit control in the web app after creation; the details panel edits the project title and author only.
- Every title sweep stacks on a second run, and `AddBookTitle` creates a new Volume (title `""`), Part or Chapter each time; the web shows the same silent success for "added" and "nothing to add".
- A Volume or Part title chapter appears as "Untitled chapter 1" in the tree and as m4b marker "Chapter 1", with Volume and Part markers stacked at the same offset; the marker fallback label is "Chapter N" at all three levels, and the front-matter Volume's marker is an empty string.
- `AddBookTitle` inserts `"By "` when the author is blank; the author is never checked.
- The pause planner's boundary skip is exact-type: a chapter whose last paragraph is a `ParagraphPause` still gets a `ChapterPause` appended after it.
- The Node menu offers Pause before / after on pause items as well as speech items, and the host accepts any item as anchor.
- The ffmpeg test endpoint writes the path it is given before probing, and no probe result is stored anywhere; the Export page reads the path but never tests it.
- A retitle (`NodeTitle`) and a project metadata PATCH neither touch the title narration nor refetch `/status`; the PATCH is not a mutation at all, so it leaves no receipt.
- No Book entity has a timestamp column and the revision is in-process only; the only build-age comparisons available today are file mtimes.
